# ADR-0011 — Text on a face

## Status

Accepted.

## Context

A printed part wants labelling: a size, a part number, a name. That has to become real
geometry, not a decal — something the slicer sees and the nozzle lays down.

This build of OCCT has no font support at all. There is no `Font_BRepFont`, no
`StdPrs_BRepFont`, nothing in the `Font_` namespace, so the usual "ask the kernel for a
text shape" route does not exist. Glyph outlines have to come from somewhere else.

## Decision

**Outlines are extracted at build time, not parsed at run time.** `tools/extract-fonts.mjs`
reads printable ASCII out of five TrueType files and writes `font-data.ts`: contours as
flat runs of integers in font units. 126 KB for five faces, nothing loaded at run time,
no font binaries redistributed, no TTF parser shipped to users, and a document layer that
stays pure and testable in Node with no assets. The tool is a self-contained TrueType
reader — `cmap` format 4, `loca`, `glyf` including composites, `hmtx` — which is less
code than taking a dependency and never runs in the app.

The five faces are DejaVu Sans, Serif, Sans Mono and Sans Condensed, plus Ubuntu
Regular, all permissively licensed; see NOTICE.md. Mono is genuinely monospaced, which
the tests assert rather than assume.

**Text reuses the whole sketch pipeline.** Glyph contours are laid out on a baseline,
scaled, flattened to polylines, and grouped into regions by containment — the same
grouping the sketcher uses, because "which loop is inside which" is the same question. A
letter's counter comes out as a hole and the dot on an `i` as its own region, and only
containment can tell those apart. The result goes through `makeFace` → `extrude` →
`boolean` exactly as a sketch would. **No new kernel operation was added.**

**The sign of the depth decides raised or sunk.** Positive stands the letters proud and
fuses them on; negative cuts them in. One field rather than a mode, because "how deep"
and "which way" are the same question about a label, and a separate toggle is a second
thing to get wrong. The tests assert that a 1 mm raised A and a 1 mm sunk A add and
remove the same volume.

**Text works out its own reading direction.** A sketch plane's in-plane X is chosen for
STABILITY — any deterministic function of the normal will do, because what matters is
that a rebuild must not rotate everything drawn on that plane. Text cannot use it: on a
top face it points along −Y, and the first label built came out reading sideways off the
edge of the part. Reading direction is world +X laid into the face, or +Y where the face
points along X and +X has nowhere to go, which gives upright text on all six faces of a
box and still depends on nothing but the normal. An `angle` value turns it about the
face's normal from there.

## Consequences

- Only printable ASCII. The whole of DejaVu would be megabytes, and a printed part is
  labelled in ASCII. Anything else falls back to `?`.
- Curves are flattened to line segments at 0.02 mm, well under a nozzle width. The
  letters are polygons, not splines — invisible at print resolution, but a STEP export
  carries polygons rather than curves.
- Regenerating the data needs the source fonts installed at the paths the tool names.
  The generated file is checked in, so a normal build does not.
- Text on a curved face is refused rather than wrapped.
